# Reflection (draft, 573 words) - personalise before submitting

Building RAM Price Tracker taught me that choosing the right tool matters as much as writing the code. My first decision was how to connect Django to MongoDB. Djongo is the package most tutorials mention, and the assessment lists it, but after reading its repository and the MongoDB documentation I chose the official django-mongodb-backend instead. Djongo translates SQL into MongoDB queries and has fallen behind current Django releases, whereas the official backend is maintained by MongoDB and targets Django 5.2 LTS. This meant more setup, because Django's built-in apps assume integer primary keys, so I had to configure ObjectId-based app configurations and generate separate migrations for the admin, auth and contenttypes apps. In return I understood what was happening underneath instead of relying on a layer that might break.

The most important design decision was how to model price history. Embedding an array of prices inside each product looks convenient, but the array grows without limit and every read of a product would drag the whole history along. I stored price records in their own collection and referenced the product by its ObjectId, then copied the current best price onto the product so that filtering and sorting stay a single indexed query. The cost is that price information now lives in two places, so I made the price records the only source of truth: saving or deleting a record recalculates the product's price. A unit test of the admin showed me how easily this kind of duplicated data can drift, because bulk deletion skipped my hook until I overrode it.

Indexes were where theory became concrete. Reading explain("executionStats") output, I saw the price-history query examine 12 documents with the compound index, against all 3,929 without it, and I noticed that the in-memory sort disappears when the index order matches the sort order. I also learned to be honest about limits: on a products collection of only 49 documents the difference is small, and the benefit appears as the catalogue grows.

Several bugs taught me more than the parts that worked first time. The brand filter silently did nothing because my form mixin validated the form before the database-driven choices existed. A discount of 9.99% was rounded to 10.0% and wrongly labelled a deal, which I fixed by comparing the exact value and truncating only for display. The compare button never enabled because my JavaScript looked inside the wrong element. Each of these was found by writing tests, either unit tests or a run in a real browser, not by looking at the page and assuming it worked. I now treat testing as a way of discovering what I have misunderstood.

The project also taught me practical habits. Connection details and secrets are read from environment variables rather than hard-coded, so the same code runs against a local MongoDB or an Atlas cluster. The README lists the installation steps for each operating system, because an application that only starts on the author's machine is not finished.

If I continued the project, I would add scheduled imports of real retailer prices, MongoDB transactions on a replica set for stronger consistency, and email notifications when a watchlist target is reached. I would also test the setup on Windows and macOS, which I have not yet done. Overall the project strengthened my understanding of non-relational modelling: the right structure depends on how the data is queried, and every convenience in a schema has a cost somewhere else.
